# XPilot architecture

XPilot is a desktop shell around x.com with an agent next to it. The agent runs on the user's own agent CLI — Codex or Claude Code — and it reaches X through a small set of tools that we control. This document explains how the pieces fit, why they are shaped the way they are, and what we considered instead.

## 1. Processes and windows

```
┌──────────────────────────── Electron main process ─────────────────────────────┐
│  settings.json   history.sqlite   tool registry   agent controller   tasks     │
│        │               │               │                 │             │        │
│        │               │        ┌──────┴──────┐   codex app-server   codex     │
│        │               │        │ tool sources│   (interactive)      (per run) │
│        │               │        │ adapter bridge│       stdio JSON-RPC          │
│        │               │        │ xview tools  │                                │
│        │               │        │ app tools    │                                │
│        │               │        └──────┬──────┘                                │
└────────────────────────────────────────┼───────────────────────────────────────┘
        IPC (sender-checked)             │ IPC (sender-checked)
┌──────────────────────┐   ┌─────────────┴──────────┐   ┌───────────────────────┐
│ Sidebar view         │   │ X view (visible)       │   │ Hidden X windows      │
│ React, sandboxed,    │   │ x.com, persist:x,      │   │ same session, one for │
│ own preload, CSP     │   │ isolated preload with  │   │ the agent, one for    │
│                      │   │ the adapter tools      │   │ scheduled runs; PDF   │
│                      │   │                        │   │ export window         │
└──────────────────────┘   └────────────────────────┘   └───────────────────────┘
```

One `BaseWindow` hosts two `WebContentsView`s: the X page on the left and our React sidebar on the right, served from a private `xpilot://sidebar` scheme so no `file://` privileges are needed. A third view is created lazily when a custom view is shown (§5): it sits between the two, over the X page, which stays loaded underneath as its data source. `computeLayout` in `src/main/layout.ts` is a pure function of window size and collapsed state; when the sidebar is collapsed it shrinks to a floating handle so the page gets the whole width.

Reads that must not disturb the user go to a hidden `BrowserWindow` on the same `persist:x` session, so it shares the login. The interactive agent and scheduled task runs each get their own hidden window so they never race each other for the page. PDF export uses a third short-lived hidden window.

Every Codex conversation is a separate `codex app-server` child process speaking newline-delimited JSON-RPC over stdio. The interactive sidebar owns one long-lived process; each scheduled task run spawns its own and tears it down afterwards. A detached watchdog process kills a child whose parent died. Each turn carries an abort signal: Stop cancels in-flight tool calls, and a turn with no activity for five minutes is failed with a visible hint.

## 2. The X adapter

X offers nothing for agents, so we make the page agent-drivable ourselves. The X view's preload runs in Electron's isolated world with `contextIsolation` and the renderer sandbox on, where page scripts cannot see or alter it. It does two things:

- **Registers adapter tools** with the main process over IPC. Each tool is a `ToolModule` with a JSON-schema `spec` and an `execute` that reads or drives the DOM. Reads use extractors in `src/preload/x/adapter/extract.ts` and `widgets.ts`; every CSS selector lives in `selectors.ts`, so an X markup change is a one-file fix. A post carries what is attached to it as well as its own text: the post it quotes (read from the nested block, and kept out of the quoting post's own text, author and time), its link cards and its images and videos. Fixtures captured from the real site in `tests/fixtures/` keep the extractors honest.
- **Tracks focus.** `computeFocus` derives what the user is looking at (a post page, a reply dialog, the posts on screen) and sends a `PageContext` to the sidebar, which prepends it to the next message as a hint. Liking a post is captured with a pointerdown snapshot, so a page script cannot write a row: the liked-posts index holds the posts the user liked themselves or asked the agent to like, and nothing else. The agent's half is written from main by `x_like_post`, which only runs once the user has confirmed it or set likes to autonomous.

Those selectors are configurable. `src/shared/selectors.ts` holds the shipped defaults and a line per key saying what it points at; the preload's `SEL` is a copy of them that `applySelectorOverrides` rewrites in place from `<userData>/selectors.json` before any tool runs and again whenever the file changes, so the call sites never know an override happened. A value the browser will not parse falls back to its default, because several call sites combine two selectors into one list that runs on every click. Only overridden keys are stored, each alongside the default it replaced. That is the sync rule: a new version's updated defaults flow through for every key nobody touched, while an override whose recorded default has since changed is kept and reported `stale`, so nothing the user fixed is silently discarded and nothing new is silently ignored. Overrides go to every X view, visible and hidden, because the adapter must read the page the same way wherever it runs; the PDF exporter has no preload, so it is handed the effective map instead.

The catalogue is split in two. Most keys only change what the adapter _reads_. Ten of them — the composer, the Post, Like and Unlike buttons, the two Bookmark buttons, the tab bar, "Show more", dialogs and toasts — are what a tool clicks, types into, or reads back to confirm an action, so moving one changes what the app does on the account. Those are `locked`: no tool can set them, only the user editing the file, and each such override is logged when the file loads. Repairing a read selector is a loop of tools rather than a guess: `xpilot_list_selectors` to see them, `x_inspect_page` for the markup X actually renders, `xpilot_test_selector` to measure a candidate, `xpilot_set_selector` to write it once the browser has accepted it.

Health is reported rather than assumed: `x_get_page_state` waits for X's layout to render and returns per-extractor `health` signals (layout, posts, article) plus `adapterHealthy` as their conjunction, and the agent is told to say so when it is false.

## 3. The tool layer

`src/shared/tools.ts` defines the contract: a `ToolSpec` (name, description, input schema, annotations) and a `ToolResult` that is either `ok(content)` or `fail(error)`. A `ToolRegistry` merges tool sources by name; later sources win, and tools annotated `internal` are callable by main but hidden from the model. There are three sources:

| Source         | Runs in                      | Examples                                                                                                                                                                                                                                                                                                                       |
| -------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| adapter bridge | the visible X view's preload | `x_get_page_state`, `x_read_visible_posts`, `x_scroll`, `x_show_new_posts`, `x_inspect_page`                                                                                                                                                                                                                                   |
| xview tools    | main, driving a view         | `x_read_post`, `x_search`, `x_read_timeline`, `x_read_bookmarks`, `x_read_news_and_trends`, `x_like_post`, `x_bookmark_post`, `x_compose_post`, `x_submit_post`, `x_navigate`                                                                                                                                                  |
| app tools      | main, app services           | `xpilot_search_history`, `xpilot_save_article_pdf`, `xpilot_list_library`, `xpilot_schedule_task`, `xpilot_read_page_styles`, `xpilot_write_page_styles`, `xpilot_list_selectors`, `xpilot_test_selector`, `xpilot_set_selector`, `xpilot_reset_selector`, `xpilot_view_api`, `xpilot_write_view_file`, `xpilot_activate_view` |

Two rules shape the xview tools. First, **background by default**: reading, searching and verifying happen in a hidden window, and only tools that the user's intent clearly points at the screen (`x_navigate`, `x_scroll`, `view: "visible"`) move the visible view. Second, **user decisions are final**: anything that writes to the account goes through the `ApprovalBroker` when the relevant setting says confirm, and a decline comes back as `status: 'cancelled_by_user'`, not as an error, so the model does not retry.

Scheduled runs get their own registry per run. By default its "visible view" is a stub that refuses, so an unattended run cannot hijack the user's screen; a task the user explicitly asked to act on their screen (`visibleWindow`) is given the real view and the adapter bridge with it, and nothing else changes. That stub says so through `isAvailable()`, so `x_compose_post` can open the composer in the run's own hidden window instead of failing: a run can post, and posting still goes through the same confirm card and the same `settings.posting` setting, in whichever window holds the draft. The same registry drops the tools that rewrite the page config — `xpilot_write_page_styles`, `xpilot_reset_page_styles`, `xpilot_set_selector`, `xpilot_reset_selector`, `xpilot_test_selector` — because both files govern every X window, survive restarts, and land on the page the user looks at. The read tools stay, so a run can report that the adapter looks broken.

Page styles are the fourth thing gated by a setting: `settings.styles.mode` is `confirm` by default, and the agent's stylesheet reaches the user on an approval card with the whole CSS on it before it reaches the page.

Tools that navigate a view and then read it run under a per-view lock, so parallel calls from the model never interleave on one hidden window. The preload's tool specs are compile-time constants shared with main, so the tool list, and the thread fingerprint derived from it, never depend on page timing.

Adding a tool is one file: export a `ToolModule` and add it to the source's list. Adding a source is a class with `list()` and `call()`.

## 4. The agent layer

An `AgentProvider` is one backend behind one interface: `start`, `send`, `interrupt`, `listModels`, `stop`, an `AgentEvent` stream, a `kind` (`codex` or `claude`) and a `capabilities` record. `createProvider(kind, deps)` in `src/main/agent/providers.ts` is the only place either is constructed. Both are handed the whole `settings.agent` slice and read their own part of it, so adding a provider adds a settings key rather than a new parameter everywhere. `settings.agent.provider` is `null` until the user picks one, and the controller then stays disconnected with "Choose a model to connect" rather than guessing.

`CodexProvider` wraps one `codex app-server` process. It sends `initialize`, starts or resumes a thread with our tool specs as `dynamicTools`, and turns server notifications into a small `AgentEvent` vocabulary the renderer understands: status, message deltas, thinking, tool started and completed, activity, web-search items, approvals. Server-initiated `item/tool/call` requests are routed to the registry and answered with the tool result, wrapped as untrusted page data.

`ClaudeProvider` drives Claude Code through the Agent SDK, which spawns the user's own `claude` binary once per turn — there is no long-lived process to hold, so `start()` only resolves the binary and decides which session the next turn continues. Our tools are published to it as an in-process MCP server (`createSdkMcpServer`), so a tool call never leaves the main process; each `ToolSpec`'s JSON schema becomes the Zod shape the SDK wants, minus its defaults, because the SDK makes a defaulted argument required at validation time while our own `runTool` is what applies defaults anyway. The turn is isolated from the user's own Claude Code: `settingSources: []` (no CLAUDE.md, no hooks, no project MCP servers), our developer instructions as the whole system prompt, auto-memory and claude.ai connectors off by environment, `permissionMode: 'dontAsk'` with only `mcp__xpilot__*` (and `WebSearch`, when the user has it on) allowed, and every built-in tool named in `disallowedTools` so a Claude Code upgrade cannot quietly add one. Streamed messages are mapped onto the same `AgentEvent`s: thinking and text deltas, `WebSearch` as a `web_search` row, and our own tools reported by the handler that runs them, which is the only place the parsed arguments exist. Sessions are ours to name: the provider generates the session id up front, so the app has a thread to record against before the CLI has run, and adopts the id the CLI reports if it differs.

The two differ in one way the rest of the app has to know about, and that is what `capabilities.toolsFrozenPerThread` says. Codex fixes a thread's tools at `thread/start`, so the controller fingerprints the tool list and starts a fresh thread when the fingerprint changes rather than resuming a thread that believes in a different tool set. Claude reads the tool list on every turn, so the same change resumes cleanly. Threads never cross backends: a thread recorded under one provider is never resumed by the other, and a conversation the other provider wrote opens read-only.

`AgentController` owns thread lifecycle: it creates the provider for the chosen backend, decides what may be resumed, switches backends (`switchProvider` stops the old one, records the choice and starts a fresh thread), probes a backend for the Settings "Connect" button with one throwaway turn, and records every event into the conversation log so the History panel can replay it.

Prompting follows `docs/agent-principles.md`: hints, not scripts. The developer instructions state a handful of rules (background by default, verify with web sources, decisions are final, two-step posting, schedule recurring requests) and leave tool selection and interpretation to the model.

Scheduled tasks live in the `tasks` table with a schedule (`every` or cron), a prompt written by the agent as complete instructions for an unattended run, and a thread mode. Each task also carries a watermark, `last_seen_post_id`: the runner reads the largest post id any `x_read_timeline` result carried during a run and stores it, so the next run's preamble can tell the model to pass that id as `sinceId` and read only what is new. `TaskManager` ticks every 30 seconds, enqueues due tasks once, and runs them one at a time; `TaskRunner` spawns a provider per run with a 10-minute limit. Tasks run only while the app is open. A run's conversation is viewable from History but read-only — the interactive agent refuses to bind to a run's thread — and while the run is still going its transcript streams into the sidebar on its own channel.

A run is hidden unless the task says otherwise. `visibleWindow` is the opt-in: the agent sets it only when the user asked for a task that acts on their screen, and then the run drives the visible view and gains the preload's screen tools, while background reads still go to the runs' own hidden window. Everything else about a run is unchanged — no task-management tools, no page-config writers, the same approvals. Because the tool list differs, a task whose `visibleWindow` changed starts a fresh thread rather than resuming one Codex fixed to a different tool set. Such a run also waits for the user: main tracks when they last used the app (pointer, keyboard or a message they sent), and a run enqueued within two minutes of that is deferred — pushed back two minutes, not a whole interval, and recorded as `deferred`. While one is executing, the sidebar carries a banner naming the task with a Stop that ends the run as `interrupted`.

## 5. Custom views

A custom view is a whole replacement UI for the X page, written by the agent and rendered over it. The user asks for one in words ("show me my timeline as cards"), the agent writes HTML, CSS and JavaScript into `<userData>/views/<name>/`, and XPilot draws it in a third `WebContentsView` laid over the X view with the X view's own bounds.

The X page stays loaded underneath. That is the whole design: a view has no network of its own, so the page below it is its data source, and its DOM must keep rendering for the adapter's reads to work. `window.xpilotView`, exposed by `src/preload/view.ts`, is the only thing a view can reach:

- `subscribe(feed, cb)` for `page` — the same `PageContext` the sidebar gets, relayed from the visible view's focus tracker — and `posts`, its visible posts, re-read with `x_read_visible_posts` every three seconds while somebody is listening, so a timeline the user scrolls stays live.
- `call(tool, args)` for an allowlist: the reads, the three drivers (`x_scroll`, `x_show_new_posts`, `x_navigate` — moving the page underneath is how a view loads more), and the four writes. Everything else, including every `xpilot_*` config, task and view tool, is refused by name. At most 20 calls per 10 seconds.
- `openInX(url)` and `back()`.

Results come back as plain tool results rather than fenced page data: this is our own UI asking, not the model reading a page.

Every call a view makes is accountable, because a view acts with no turn around it and no model to attribute it to:

- **It is traced.** The bridge puts a `tool.started`/`tool.completed` pair on the interactive agent's own event stream under the name `view:<tool>`, so it renders as a tool row in the sidebar and is written to `conversation_events` like any other call. A surface that acts on the account without a transcript is a surface the user cannot audit.
- **Its cards say whose they are.** `ApprovalRequest.origin` is `{ kind: 'agent' }` or `{ kind: 'view', name }`, carried from the bridge through `registry.call` into the tool's context (never into the model-facing spec), and a view's card is drawn with its own header line — "Requested by the custom view "<name>"" — and a different frame.
- **Autonomous modes do not reach it.** `x_like_post`, `x_bookmark_post`, `x_compose_post` and `x_submit_post` called from a view always raise the card, whatever `likes.mode`, `bookmarks.mode` and `posting.mode` say: that consent was given to the agent, whose every call is a row the user can scroll back through. `x_compose_post` asks before it opens the composer at all, because a view can fill one with its own text and simply stop.
- **A preview may only render.** Until the "Keep this view?" card is answered the bridge allows the reads and the two feeds; the drivers and the writes answer `This view is a preview; keep it first`.
- **A card cannot be hidden.** Any approval request expands a collapsed sidebar, which otherwise renders no cards at all while the canvas owns the whole window.
- **A view's `x_navigate` is narrower than the user's allowlist.** Only https on x.com or twitter.com: the allowlist holds `t.co`, and a short link is an attacker-chosen redirect the page policy would hand to the system browser. Taking a view off the screen puts the X page back on `/home` if the view left it on a composer or an intent URL.

The isolation is the point, because a view is code a model wrote out of what a page said. It runs in its own session (`views`, not `persist:x`, so it has none of the X cookies), sandboxed and context-isolated, with every permission denied, every download refused, and a navigation policy that cancels anything outside `xpilot://views/<active>/` rather than routing it to the browser. Its files are served on that session alone — the default session, which is the sidebar's, serves only the sidebar bundle — under a CSP with `default-src 'none'` and `connect-src 'none'`, carried by every response including 404s and the shelf: no network, no inline script, pictures and video only from X's own CDN, and modules only from the view itself and `xpilot://lib/`, a fixed shelf of exactly three files from the installed `three` package (the scheme is registered `corsEnabled` so a module import across the two hosts is possible at all, and only the shelf answers with an allow-origin header). A symlink is never served, matching the store, and nothing agent-written ever runs inside x.com.

CSP does not govern WebRTC, and `RTCPeerConnection` reaches an arbitrary host and port with attacker-chosen bytes in a STUN username and hostname — which would make "no network" false. No Chromium switch takes it away: `--disable-features=WebRTC`, `--disable-features=RTCPeerConnection`, `--disable-blink-features=PeerConnection|RTCPeerConnection|WebRTC` and `--disable-webrtc` were each measured and left `typeof RTCPeerConnection === 'function'`, as did a `webrtc 'block'` CSP directive. So `src/preload/view.ts` removes it from the page's own world before any view script runs: `webFrame.executeJavaScript` at preload time defines the ten `RTC*` constructors and `navigator.mediaDevices`/`getUserMedia` as non-writable, non-configurable `undefined` on `window` and `globalThis`. A worker needs no hook — those constructors are `[Exposed=Window]` and are already absent there — and the CSP allows no frames, so the main world is the whole surface.

All views share one origin, `xpilot://views`, so a view can `import()` another view's files and they share `localStorage`. That is accepted for now: every view is written by the same agent for the same user, none holds a secret the others do not, and cross-view _navigation_ is still cancelled by the canvas policy. Giving each view its own host (`xpilot://view-<name>/`) is the fix if a view ever holds something another should not read.

Everything a view does wrong is handled in one place, because the failure the user sees has to say which of them it was. `did-fail-load` on the main frame, a response the scheme handler answered 4xx (an `index.html` deleted under a running view), a renderer that died, a preload that failed, and a renderer that has been wedged for ten seconds are all fatal: the canvas comes off, the X page underneath is what the user is looking at again, `settings.views.active` is cleared so the next start is on x.com, and a `view.error` event carries `{ view, phase: 'load' | 'crash' | 'unresponsive' | 'runtime', message, at }` to the sidebar. A wedge is only fatal after those ten seconds — a long frame is not a failure, and `responsive` inside them leaves the view alone. Errors the view's own scripts throw are not fatal at all: a view is a page, and an exception in one render is not a reason to take the user's screen away. The sidebar's banner says `Custom view "<name>" failed: <message>` and offers "Fix it", which sends the user's own message — the view, the phase, the message, and the two tools that read a view's files and its console — through the same `send` path the composer uses, so the repair is a turn in the transcript rather than something the app did behind their back.

Chromium reports an uncaught error only to the world whose script threw, so a listener in the preload's isolated world never sees what a view threw. `src/preload/view.ts` installs the `error`, `unhandledrejection` and `securitypolicyviolation` listeners in the page's own world with `webFrame.executeJavaScript`, beside the WebRTC removal, and they hand each one over as a `CustomEvent` whose detail is a JSON string — a DOM event crosses the boundary where an object would not. The preload relays it on `view:error`, at most ten in ten seconds with a kilobyte per message; the bridge checks the sender against the canvas, parses and cuts it again, and budgets it again, because a view is agent-written code and its rate is not ours. Main appends it to the ring buffer with `file:line:col` and raises the banner for the first error after an activation and at most once every thirty seconds after that. More than twenty in a minute, or a second crash or wedge inside five minutes, ends the view instead: `too many errors; deactivated`. A view is announced as active before its page is loaded rather than after, so an error thrown on the way up arrives after the view it is about — and so the bridge's subscriptions are reset before the new document makes its own rather than just after.

`xpilot_view_console` is what the agent debugs from, so it is bounded on every axis a view could exhaust: fifty entries by default and two hundred at most, five hundred characters a line, twenty kilobytes in all, newest kept. Two change-triggered reloads that fail to load in a row stop the third, so a view that cannot load cannot spin with the watcher.

Activation mirrors page styles: in `confirm` mode the view goes on screen as a preview — able to read and draw, and nothing else — and a "Keep this view?" card offers Keep / Adjust… / Revert, with the same ten-minute backstop; Keep persists `settings.views.active`, Adjust returns the user's note, Revert is `cancelled_by_user`. The store watches the folder, so writing a file — by the agent or by the user in their own editor — reloads the view. Console messages, preload failures, dead renderers and the errors a view's own scripts threw go to a 200-entry ring buffer per view that `xpilot_view_console` reads, since a view has no devtools; `xpilot_view_inspect` runs a capped snippet in it to show what it actually rendered. A load failure or a crash falls back to the X page and says so in the sidebar (below). On startup the remembered view comes back once x.com has loaded, or the setting is cleared if it is gone. Scheduled runs get the read and list tools only.

## 6. Data

- `settings.json` holds user settings, window bounds and the chosen provider, validated with zod and written atomically. `agent-state.json` beside it holds the live thread: its id, the tool fingerprint it was started with, and which provider owns it.
- `history.sqlite` (Node's built-in `node:sqlite`, WAL mode, versioned migrations) holds liked posts with an FTS5 index, the PDF library, conversations and their event logs, and scheduled tasks. Tool output in the transcript is capped, and a retention policy in Settings prunes old conversations; the database size is shown there.
- PDFs go to `~/Documents/X Pilot` by default; paths are contained to that folder before anything is written or opened.
- Nothing about the X account leaves Electron's session store. Authentication belongs to the agent CLI: Codex's to `codex login`, Claude's to `claude`, and Claude Code keeps its own session transcripts under `~/.claude/projects/` keyed by our workspace directory.

## 7. Security model

The X page is untrusted remote content that runs third-party scripts, and the agent can write to a logged-in account. The defences, from the outside in:

- **Renderer isolation.** All views run with `contextIsolation` and the Chromium sandbox; preloads are self-contained bundles, and the sidebar has a strict CSP in production. Packaged builds set Electron's fuses: cookies are encrypted with a key in the user's keychain, the binary cannot run as Node, `NODE_OPTIONS` and inspector arguments are ignored, and only the integrity-checked asar can be loaded.
- **Navigation policy.** Every WebContents the app creates gets the policy, including popups opened by popups and the PDF exporter, and it covers subframes. In-app navigation is limited to https on x.com, twitter.com and t.co. Login providers open in a popup without our preload. Everything else goes to the system browser through a rate-limited `shell.openExternal`; t.co links are resolved in main with https-only, bounded hops. `window.open` is denied everywhere by default.
- **Permissions.** Session permission handlers deny everything except fullscreen and sanitised clipboard writes, and grant those only to allowlisted https origins in the main frame.
- **IPC.** Every handler checks the sender's `WebContents` id and validates payloads with zod, including settings patches. Liked-post events are accepted only from trusted user clicks, with capped fields and a rate limit. The sidebar API is only reachable from our own renderer.
- **Prompt injection.** Page text reaches the model in three ways: the focus hint, tool results, and the prompts of scheduled tasks. All of it, including author names and URLs, is fenced as untrusted data with escaped delimiters, and the instructions say so. Authorship comes from permalinks, never from display names. Writes are gated by settings: posting and likes confirm by default, the approval card cannot be scrolled away from its buttons, and Codex's own command approvals stay on. `x_navigate` refuses URLs that act on load, such as logout, settings and intents.
- **Containment.** PDF filenames are derived from the requested URL and sanitised metadata, the export aborts if the page moved, and paths are checked against the library folder; only `.pdf` files inside it can be opened. Profile files are created private to the user.
- **Page config.** Two files in the profile — `page-styles.css` and `selectors.json` — are editable by the user and writable by the agent, and both reach a logged-in x.com. CSS is a deception primitive, not a cosmetic one (an invisible overlay steals a real click; `display: none` steers the layout-derived focus hint), so an agent-written stylesheet is confirmed by default with the full CSS on the card, and it is checked before it is applied: comments stripped, backslash escapes and every function-shaped way of naming an off-page resource refused, 64 KB cap, applied to the visible view only. The selectors that decide what the app _clicks_ rather than what it reads are locked against every tool; the rest are probed on the page before they are written, and an unparsable value falls back to the shipped default. Neither file can be written by a scheduled run. Both are read from memory, refuse symlinks, cap at 256 KB, and a read that fails keeps the last good value rather than being renamed aside — the synchronous startup reply always answers, whatever is on disk.
- **The agent CLI.** Either binary — `codex` or `claude` — is taken from an explicit setting, PATH, or the login shell before any guessed directory, and must be a regular file owned by the user or root that nobody else can write. An explicit setting is a choice, not a hint: when it points at nothing, or at something that fails the check, the search stops there and the setup card names the path, rather than quietly starting a different install. The path is only ever written by the file picker in Settings, after that check; it is deliberately absent from the settings patch schema, so no renderer can point the app at an executable of its choosing. A Claude turn runs with `permissionMode: 'dontAsk'` and every built-in tool denied, so the model reaches nothing but our tools. **Codex has no equivalent, and that is a real gap.** A Codex thread inherits the user's own `~/.codex/config.toml`, MCP servers included, so an unattended run can reach tools XPilot never granted — a scheduled run was seen calling OpenAI's bundled computer-use server to try to drive a browser. The app-server protocol has no switch for it: `thread/start`'s `config` is a deep merge of config.toml overrides, so `mcp_servers: {}` is accepted and does nothing, and while `mcp_servers.<name>.enabled = false` does disable a named server, servers a Codex plugin provides are not in `mcp_servers` at all and naming one fails the config load outright. The only complete fix is running the child with its own `CODEX_HOME`, which also takes over its login and history; it is open (see `docs/release-todo.md`). Our tools are the whole surface on Claude and the intended surface on Codex.
- **Custom views.** A view is agent-written code, so it runs where it can do nothing: its own session with no X cookies, sandboxed, every permission denied, every download refused, a CSP with no network and no inline script, WebRTC removed from its world by the preload because no policy covers it, and a navigation policy that cancels anything outside the view it is showing instead of handing it to the browser. It reaches the app only through `window.xpilotView`, whose tool allowlist is sender-checked against the canvas's own WebContents id and budgeted at 20 calls per 10 seconds. What it does there is accountable: every call is a `view:<tool>` row on the agent's event stream and in the conversation, every card it raises names the view that asked, the four account writes always confirm however the autonomous settings are set, a view that has not been kept yet may only read, and any card expands a collapsed sidebar. Its `x_navigate` is limited to https on x.com and twitter.com — never a short link — and taking it off screen leaves the X page on `/home` rather than on a composer it filled. Files are contained to `<userData>/views/<name>/`, capped per file and per view, limited to eight text extensions, written atomically and privately, and never read or served through a symlink. Showing a view takes over what the user is looking at, so it is confirmed by default like a stylesheet, and a scheduled run may neither write one nor show one.
- **Dev-only switches** (test harness, DevTools Protocol port, custom start URL, custom profile) are ignored in packaged builds.

Residual risks worth knowing: a prompt injection can still steer read-only tools and anything the user set to autonomous; the DOM adapter breaks when X changes markup, which shows up as `adapterHealthy: false`; and scheduled tasks act without a human present, by design — including, when the user asks for it, on the window they are looking at, which is why such a run is opt-in per task, defers while the user is active, and is stoppable from a banner.

## 8. The renderer

The sidebar is a small React app. State is a reducer over `AgentEvent`s, so a live turn and a replayed conversation render through the same code. Consecutive tool calls collapse into one group, thinking collapses to one row per turn, and agent messages render as Markdown with links routed by the same policy as page links.

## 9. Alternatives we considered

**Electron shell vs browser extension.** An extension could inject the same adapter into x.com in the user's normal browser, but it cannot spawn Codex, cannot open a hidden same-session window, cannot save PDFs to disk, and would depend on the browser's extension APIs for the sidebar. Electron gives us the process model and the hidden windows at the cost of shipping a browser.

**`WebContentsView` vs `<webview>` tag vs iframe.** An iframe cannot host x.com. The `<webview>` tag is discouraged by Electron and blurs the preload boundary. Two `WebContentsView`s in a `BaseWindow` keep the X page and our UI in separate processes with separate preloads and let the layout be a pure function.

**DOM adapter vs X's private API vs computer use.** Reading X through its GraphQL endpoints with the session cookies would be more robust to markup changes and trivially concurrent, but it depends on undocumented endpoints and looks like automation to anti-abuse systems. Driving the page by screenshots and clicks is general but slow, expensive and brittle. A DOM adapter behind a stable tool surface is the middle path: selectors change occasionally, and when they do the fix is one file with a fixture.

**Codex app-server vs calling a model API directly vs an MCP server.** Calling a model API directly would mean our own agent loop, our own auth and billing, and no reuse of the user's Codex setup. Exposing our tools as an MCP server that Codex connects to would work, but it inverts control: the app would not know when a turn starts or ends, could not stream activity, and could not resume threads. The app-server protocol gives us threads, streaming, approvals and client-supplied tools over stdio, with the user's existing login. Claude Code is the second backend behind the same `AgentProvider` interface.

**Claude: an MCP server subprocess vs an in-process SDK server, and the SDK's bundled binary vs the user's.** The Agent SDK takes our tools either as a stdio MCP server it spawns or as an in-process one (`createSdkMcpServer`); we use the in-process form, because a subprocess would need its own channel back to the registry, the approvals and the windows that only exist in main, and every tool call would cross a process boundary for nothing. The same SDK bundles a Claude Code binary per platform as optional npm dependencies, and we ignore it in favour of `pathToClaudeCodeExecutable` pointing at the `claude` the user already installed and logged in: it is the login they have, it stays current without our releases, it makes the two backends behave alike (both are the user's own CLI, found the same way and checked the same way), and it keeps ~50 MB of binaries out of the app, which `electron-builder.js` excludes explicitly.

**One Codex process per task run vs one multiplexed process.** The protocol is thread-addressed, so one process could serve everything and avoid per-run spawn latency. We chose a process per run so a wedged or crashed unattended run cannot take the user's interactive session down with it.

**Owning the transcript in SQLite vs replaying Codex's thread.** Rebuilding the UI from Codex's own thread on open would avoid duplication, but it welds the UI to one provider and loses everything when a thread expires. Owning the event log makes the History panel, task-run records and full-text search possible.

**`node:sqlite` vs better-sqlite3.** The built-in module needs no native build step per Electron version and ships FTS5. It is still marked experimental by Node, so the store is kept behind a small class so it could be swapped.

**A page-side WebMCP polyfill.** Early versions also installed a `document.modelContext` polyfill in the page's main world so that tools registered by X or an embedded page would surface to the agent. No site registers such tools, our own adapter tools never used that path (they live in the isolated world precisely so page scripts cannot tamper with them), and the polyfill was a main-world surface any script on x.com could reach. We removed it. The adapter tools keep the WebMCP tool shape, so if X ever ships the real API it can be consumed alongside them.

**A custom view over the page vs inside it.** The cheapest way to let the agent restyle X wholesale would be to inject its code into x.com, as the page stylesheet already does with CSS. We refused: script in that page runs with the session's cookies, next to the user's real controls, and a model that wrote it from what a page said would be one prompt injection away from acting on the account. Putting the view in its own network-less session over the page, with the page reachable only through the same tools the agent already has, keeps agent-written code on the far side of every boundary we spent the rest of this document building. The cost is that a view can only show what a tool can read, which is also what keeps it honest.

**Principles vs scripted flows in the prompt.** Enumerating every way a user might refer to the post on their screen would be brittle and token-hungry. The instructions state principles and provide the current page as a hint; the model deduces the rest. See `docs/agent-principles.md`.

## 10. Known limitations

- A hard kill of the app relies on a detached watchdog to stop the Codex child; a normal quit stops it directly. Claude's child lives only for the turn, and the turn's abort controller ends it.
- Web search inside either CLI cannot be gated per query; interactive runs show every query in the sidebar, and scheduled tasks have web search off unless the task asks for it.
- macOS only for now; passkeys need a signed build with a provisioning profile (see `docs/passkeys.md`).
