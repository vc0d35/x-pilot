# Changelog

All notable changes to XPilot are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Agent sidebar next to x.com, driven by your local Codex CLI, with a per-conversation transcript and history.
- Page tools the agent uses instead of raw automation: reading the timeline, posts, threads, X Articles, profiles, notifications, and the Today's News and What's happening widgets.
- Background reads in a hidden window, so the agent can open and read a post without moving the page you are on.
- Search over the posts you liked, stored locally in SQLite.
- Save posts and X Articles as PDFs in a library folder under Documents.
- Posting, replying and liking on your behalf, asking for confirmation by default.
- Scheduled tasks that run while the app is open, isolated from the window you are using.
- Touch ID passkey login for signed builds with a provisioning profile (see `docs/passkeys.md`).
- Help menu with "Check for Updates…" and "Report an Issue…".
- `npm run dist` produces DMG and ZIP artifacts for arm64 and x64; tag pushes publish a draft GitHub release.

- Stop cancels in-flight tool calls; turns idle for five minutes are failed with a hint. Codex clarifying questions appear as a card in the sidebar. Transcript retention and database size in Settings. Scheduled tasks opt in to web search per task. Page health reported per extractor.

- Replies: `x_read_post` answers with `ancestors` (the posts a reply replies to, oldest first), `thread` (the author's continuation) and `replies` (everyone else's, more with `pages`), and a post carries `inReplyTo` wherever X shows a "Replying to" line, so a custom view can draw a conversation.
- Notifications: `x_read_notifications` reads the Notifications page (All or Mentions) as typed entries with stable ids — replies and mentions as posts, likes, reposts, follows and "new posts from" as X's own line about who did what — and `x_open_notification` opens one by id and returns the post it is about, which those entries carry no link to. Page state and page context carry `unreadNotifications` from the navigation bar's badge, so a custom view can show the count and go from a notification to its post.
- Fixed: a post the user had liked read as having 0 likes, because its stats label says ", Liked" and the comma was taken for a count.
- Posts carry `liked` and `bookmarked`, read from their own buttons, and their stats count bookmarks; `x_like_post` and `x_bookmark_post` answer with the state and the count the page shows after the click, so a custom view can draw like and bookmark toggles and update its counts at once.
- Bookmarks: `x_bookmark_post` saves or removes a post's bookmark, and `x_read_bookmarks` scrolls the user's Bookmarks page and returns what it saw. Bookmarks are private to the user, so they are a way to save something for later without a public signal; a new "Bookmarks" setting confirms each one by default, and set to autonomous a scheduled run can bookmark unattended.
- Page styles: a user-editable `page-styles.css` applied to the X view before it renders; the agent can read, replace or reset it, with an Apply card by default.
- Custom views: the agent can write a whole replacement UI for the X page into `<profile>/views/<name>/` and XPilot renders it over x.com in its own sandboxed window, with no network and no X cookies. A view reads the page underneath through `window.xpilotView` — live `page` and `posts` feeds plus an allowlist of read, driver and (confirmed) write tools — and nothing else; agent-written code never runs inside x.com. Activating one is previewed and confirmed like a stylesheet, the active view is remembered across restarts, files reload the view as they are written (and only for a change made since it went on screen: a reload drops any call the view has in flight, so the writes that preceded showing it are not one), and `xpilot://lib/` ships three.js for views that want it. New tools: `xpilot_view_api`, `xpilot_list_views`, `xpilot_read_view_file`, `xpilot_write_view_file`, `xpilot_delete_view`, `xpilot_activate_view`, `xpilot_deactivate_view`, `xpilot_view_console`, `xpilot_view_inspect`.
- Custom views handle their own failures: a view that will not load, whose renderer dies, whose preload fails or that stops responding for ten seconds falls back to the x.com page underneath, is forgotten for the next start, and raises a banner in the sidebar saying which of those it was. Errors a view's own scripts throw — uncaught exceptions, unhandled rejections and content-policy refusals — are relayed with `file:line:col`, kept with the view's console log and shown in the same banner while the view stays on screen; more than twenty in a minute, or a second crash inside five minutes, takes it off with "too many errors; deactivated". Both banners offer "Fix it", which sends the failure to the agent as your own message and asks it to read the view and repair it. `xpilot_view_console` is bounded (50 entries by default, 200 at most, 500 characters a line, 20 KB in all), bridge calls inside a view never throw across the bridge, and both starter views handle their own errors — the three.js one falls back to a text list where WebGL is unavailable. A view's own files are served `no-store` and its reload ignores the cache, so writing a file shows the file that was written rather than Chromium's copy of the last one.
- Configurable selectors: `selectors.json` overrides the adapter's read selectors, kept across app updates and flagged stale when a shipped default changes; the agent can list, test, inspect markup, set and reset them. Action selectors are locked to hand edits.

### Security

- Renderer sandbox and a production CSP for the x.com view, hardened `webContents` defaults, and dev-only switches gated on unpackaged builds.
- Permission handlers, global `window.open` denial, external-link rate limiting and a single-instance lock.
- PDF writes contained to the library folder, and only PDFs may be opened from it.
- Prompt-injection fencing around page content, tool-list stability checks, and validation of adapter tool specs.
- Custom views security review fixes: WebRTC removed from a view's world before any of its code runs (no content policy governs it, and no Chromium switch takes it away), so a view really has no network; every tool call a view makes is a `view:<tool>` row on the agent's stream and in the conversation; a card a view raised says which view asked and is drawn as its own; the four account writes from a view follow the user's likes, bookmarks and posting settings (a card under confirm, none under autonomous, since a kept view's every call is traced) and `x_compose_post` asks before it opens a composer unless posting is autonomous; a view that has not been kept yet may only read and draw; any approval card expands a collapsed sidebar; a view's `x_navigate` is limited to https on x.com and twitter.com, never a short link; taking a view off screen leaves the X page on `/home` rather than on a composer it filled; downloads from a view are refused; `xpilot_view_inspect` is bounded whatever the view's markup does; and on the `xpilot://` scheme, views are served only on the views session, symlinks are never served, every response carries the view CSP, and `.md` is served as markdown.
- Whole-application security review fixes: Electron fuses set in packaged builds (encrypted cookies, no run-as-node, no NODE_OPTIONS or inspect arguments, asar-only with integrity), profile files private to the user, Codex located from PATH and the login shell before guessed directories and only as a safe executable, settings patches validated, every page-derived field fenced before it reaches the model, scheduled-task prompts fenced in unattended runs, navigation policy on every window including popups of popups and the PDF exporter, subframes covered, permissions scoped to allowlisted origins, untrusted clicks ignored by like capture with capped and rate-limited payloads, authorship derived from permalinks only, likes confirm by default, action URLs refused by `x_navigate`, bounded approval cards with pinned buttons, deceptive link text labelled with its real host, release workflow pinned by SHA and refusing unsigned builds unless explicitly dispatched.
